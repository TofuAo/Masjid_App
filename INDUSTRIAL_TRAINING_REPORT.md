## 1.2 Organization Background 

MASJID NEGERI SULTAN AHMAD 1 is a prominent Islamic institution located in Kuantan, Pahang, Malaysia. The masjid serves as a central hub for Islamic education, community services, and religious activities in the region. The organization focuses on providing comprehensive Islamic education through its madrasah system, managing various classes and programs for students of different age groups and levels.

The masjid operates several key programs including:
- **Kelas Pengajian (Study Classes)**: Offering various levels from ASAS (Basic), PERTENGAHAN (Intermediate), to LANJUTAN (Advanced) levels
- **Student Management**: Managing hundreds of students enrolled in different classes
- **Teacher Management**: Coordinating with multiple teachers (ustaz and ustazah) who teach different subjects
- **Administrative Services**: Handling fees, attendance, exams, and results management

The organizational structure consists of several main departments and functions:
- **Administration Department**: Handles overall management, planning, and coordination
- **Education Department**: Manages classes, teachers, and curriculum
- **IT/Development Department**: Responsible for digitalization and system development
- **Finance Department**: Manages fees, payments, and financial records
- **Operations Department**: Handles daily operations and maintenance

As a Software Developer Intern, I am under the IT/Development department which is mainly responsible for software development and system implementation to digitize the masjid's operations. Under this department, I work on full-stack web development projects focusing on modern web technologies to create a comprehensive management system. Hence, I am mainly focusing on frontend and backend development which develop web applications using frameworks like React for frontend and Node.js with Express.js for backend.

The main objective of establishing the IT/Development department is to modernize the masjid's operations by replacing manual record-keeping systems with a digital platform. This digital transformation aims to improve efficiency, reduce errors, and provide better services to students, teachers, and administrators.

## 2.5 Problems Encountered

During the development of MyMasjidApp, I encountered several challenges that required creative problem-solving and technical expertise. These challenges provided valuable learning experiences and helped me develop better problem-solving skills.

### Problem 1: Payment Gateway Integration Complexity

**Description:** 
Integrating multiple payment gateways (iPay88, eGHL, PayNet Direct) with different APIs and response formats was one of the most challenging aspects of the project. Each payment gateway has its own unique:
- Authentication method (API keys, merchant IDs, signatures)
- Request format (JSON, XML, form data)
- Response structure (different field names, status codes)
- Webhook handling mechanism (different callback URLs, signature verification methods)
- Error handling approach (different error codes and messages)

The complexity was further increased by the need to support multiple payment methods (FPX, DuitNow QR, DuitNow Request, E-Wallets) across different gateways, each with its own implementation requirements.

**Impact:** 
- Delayed payment module development by approximately 1 week
- Required extensive testing with each gateway's sandbox environment
- Complex error handling for different gateway responses
- Increased development time for debugging payment flows
- Required additional documentation for each gateway integration
- Needed to handle edge cases specific to each gateway

**Learning Experience:**
This challenge taught me the importance of creating abstraction layers when working with multiple third-party services. It also highlighted the need for comprehensive testing and error handling in financial transactions.

### Problem 2: Yearly Database System Implementation

**Description:** 
Implementing a yearly database system where each academic year has its own database while maintaining data consistency and relationships was a complex architectural challenge. The system needed to:
- Create a new database for each academic year
- Copy relevant master data (students, teachers, classes) to the new year database
- Reset transactional data (fees, attendance, results) for the new year
- Maintain referential integrity across database boundaries
- Handle queries that might need to access multiple year databases
- Ensure data consistency during the migration process
- Preserve historical data in archived databases

The challenge was compounded by the need to handle edge cases such as:
- Students who continue from previous year
- Teachers who teach multiple years
- Classes that span across years
- Data migration failures and rollback scenarios

**Impact:**
- Required careful planning and design of database migration process
- Complex queries to handle cross-database operations
- Risk of data inconsistency if migration not handled properly
- Increased complexity in application logic to determine which database to query
- Need for comprehensive testing of migration scripts
- Additional time required for database design and implementation

**Learning Experience:**
This challenge taught me about database architecture design and the importance of planning for scalability and data separation. It also highlighted the need for thorough testing of data migration processes.

### Problem 3: Role-Based Access Control (RBAC)

**Description:** 
Implementing a comprehensive Role-Based Access Control (RBAC) system with multiple roles (Admin, Teacher, Student, IB - Imam Bilal) and different permission levels for each module was challenging. The system needed to:
- Define permissions for each role across all 13 modules
- Implement middleware to check permissions before allowing access
- Handle role-based UI rendering in the frontend
- Manage role-based data filtering (e.g., teachers can only see their own classes)
- Handle role transitions (e.g., student becoming teacher)
- Implement permission inheritance and hierarchy
- Ensure security at both frontend and backend levels

Each role had different access requirements:
- **Admin:** Full access to all modules and administrative functions
- **Teacher:** Access to assigned classes, student management for their classes, attendance marking, results entry
- **Student:** Access to own profile, attendance records, fee status, exam results
- **IB (Imam Bilal):** Specialized access to specific administrative functions

**Impact:**
- Complex middleware implementation requiring careful design
- Required careful route protection at both API and frontend levels
- Extensive testing for each role's access rights across all modules
- Increased development time for permission checking logic
- Need for comprehensive documentation of role permissions
- Potential security vulnerabilities if not implemented correctly

**Learning Experience:**
This challenge taught me about security best practices and the importance of implementing access control at multiple layers. It also highlighted the need for thorough testing of security features.

### Problem 4: Real-time Payment Status Updates

**Description:** 
Handling asynchronous payment notifications from payment gateways and updating payment status in real-time was challenging. The system needed to:
- Receive webhook notifications from multiple payment gateways
- Verify webhook signatures to ensure authenticity
- Handle webhook delivery failures and retries
- Implement polling mechanism as fallback for missed webhooks
- Reconcile payment status between gateway and local database
- Handle race conditions when multiple notifications arrive
- Manage idempotency to prevent duplicate processing
- Update user interface in real-time when payment status changes

The challenges included:
- Webhooks might be delayed or fail to deliver
- Webhook signatures need to be verified for security
- Multiple webhooks might arrive for the same payment
- Payment status might differ between gateway and local database
- Need to handle edge cases like partial payments, refunds, and cancellations

**Impact:**
- Required webhook verification and security implementation
- Needed fallback mechanisms (polling) for failed webhooks
- Complex payment status reconciliation logic
- Increased complexity in payment flow handling
- Need for comprehensive logging and monitoring
- Additional time required for testing webhook scenarios

**Learning Experience:**
This challenge taught me about asynchronous programming, webhook handling, and the importance of implementing robust error handling and fallback mechanisms for critical business processes.

### Problem 5: Google Forms Integration

**Description:** 
Integrating Google Forms for attendance input required understanding Google Forms API, webhook handling, and data mapping. The integration needed to:
- Set up Google Forms webhook to receive form submissions
- Parse form submission data from Google's format
- Map form fields to database columns
- Validate data before inserting into database
- Handle duplicate submissions
- Verify webhook authenticity
- Handle errors and edge cases

The challenges included:
- Google Forms API documentation complexity
- Different data formats from Google Forms
- Need to map form responses to database schema
- Handling special characters and encoding issues
- Validating student IC numbers and other data
- Ensuring data consistency with existing records

**Impact:**
- Required learning Google Forms API and webhook handling
- Complex data mapping and validation logic
- Webhook security and verification implementation
- Additional time for testing form submissions
- Need for error handling and data validation
- Potential data inconsistency if mapping incorrect

**Learning Experience:**
This challenge taught me about third-party API integration, data transformation, and the importance of data validation when receiving data from external sources.
